# 故障隔离：让代理挂掉不拖垮全网

> **部署形态声明（先读这条，否则参数会对不上）**
>
> 本文是 **iptables 形态**的实测记录：`firewall_mod=iptables`、`firewall_area=3`、`config.yaml` 中 `tun.enable: false`（纯 Redir，无 TUN）、fwmark 实际生效值 `0x1ed8`、fake-ip 段 `198.18.0.1/16`。
>
> 本仓库中另外几份文档记录的是 **nftables / fw4 形态**：`docs/R3G_ShellCrash_故障排查手册.md`、`docs/部署与排障手册.md`、`docs/标准设置手册.md`、`docs/R3G完整配置教程.md`、`engineering/configs/nftables规则.txt`，其 fwmark 为 `0x1ed4`、`firewall_area=1`、`tun.enable: true`、fake-ip 段 `28.0.0.0/8`，且会同时给 TCP 与 UDP 打标。
>
> **这不是版本笔误，是同一台 R3G v1 在不同固件 / ShellCrash 防火墙后端下的两套真实部署。** 两套参数不可混用：照 A 文档改 B 配置，会出现「规则写得对、流量就是不进来」或「进来了但环路」的现象。动手前先用下面的命令确认自己当前是哪一套：
>
> ```sh
> grep -E '^(firewall_mod|firewall_area|fwmark)=' /etc/ShellCrash/configs/ShellCrash.cfg
> iptables -t nat -L shellcrash -n 2>/dev/null | grep -i mark     # iptables 形态有输出
> nft list table inet shellcrash 2>/dev/null | head -20           # nftables 形态有输出
> ```
>
> 哪条命令有输出，就按哪套参数读文档。

> 本文讨论一个被大多数透明代理教程忽略的问题：**当代理内核失效时，家庭网络会不会一起断？**
>
> 结论先说：会，而且断得比想象的彻底——因为 DNS 也在这条链上。本文记录一套三层隔离设计，目标是把"代理故障"的影响面压缩到"仅境外流量不可用"，而不是"全屋断网"。
>
> 适用范围：R3G v1（MT7621A）+ OpenWrt + ShellCrash，Redir 模式（`config.yaml` 中 `tun.enable: false`），非 TUN。

---

## 1. 问题定义：失效有两种，危害等级差一个数量级

很多人把"代理挂了"当成一件事，实际上是两种完全不同的失效模式，处置策略和危害程度完全不同。

| 失效模式 | 内核状态 | 7892 端口表现 | 客户端感受 | 危害 |
|---|---|---|---|---|
| **进程退出 / 崩溃** | 进程不存在 | 无人监听 → TCP 立即返回 RST | 秒级失败，立刻回退重连 | **低** |
| **进程卡死 / 无响应** | 进程还在，但不处理请求 | 端口在监听，无应答 | 长时间挂起直到超时 | **高** |

第二种是真正的灾难：连接不会快速失败，而是一直等，客户端表现为"网页转圈、游戏掉线、应用假死"，用户第一反应是"网络坏了"，排查方向直接被带偏。

**关键推论**：任何守护脚本如果只检查"进程是否存在"，就永远发现不了第二种情况。这是绝大多数自制守护脚本的失效点。

### 更隐蔽的一层：DNS 也在代理链上

即使流量分流做得再干净，`DNS` 这一环仍然在代理内核里。当配置启用 `fake-ip` 模式时：

```
客户端 DNS 查询 → R3G 劫持 → CrashCore:1053 → 返回 198.18.x.x 假地址
客户端连接 198.18.x.x:443 → 被劫持到 7892 → CrashCore 查映射 → 按规则分流
```

也就是说，**国内域名的解析同样依赖 CrashCore**。它一卡死，国内域名也解析不出来，用户看到的现象是"国内网站也打不开了"——此时分流规则里写了多少条 `DIRECT` 都毫无意义。

这是本文最重要的一条认知：**"国内不受影响"不是由分流规则保证的，而是由 DNS 链路和故障兜底共同保证的。** 只做流量分流、不管 DNS 兜底，等于把整张网押在一个进程上。

## 2. 三层隔离设计

按影响面从内到外，分三层处理。

### 第一层：规则层隔离 —— 让国内流量根本不进内核

分流规则的作用不是"故障时保底"，而是**让国内流量从一开始就不参与代理决策**。

实测配置的核心规则链：

```
IP-CIDR,<国内CDN段>,自动选择,no-resolve    # 18 条特例前置，均在兜底之前
GEOIP,CN,DIRECT                            # 国内目标直连（第 536 条）
MATCH,自动选择                              # 其余走代理（第 537 条，末条）
```

命中 `GEOIP,CN,DIRECT` 的流量，最终走的是内核直接转发，不经过 7892 的用户态处理。这一层在**内核正常运行**时就能提供隔离：

| 场景 | 国内流量 | 境外流量 |
|---|---|---|
| 某个代理节点挂了 | 不受影响（走 DIRECT） | 受影响（组内切换或失败） |
| 代理组全部失效 | 不受影响（走 DIRECT） | 全部失败 |
| **内核卡死** | **受影响**（DNS 断 + 80/443 仍被劫持） | 全部失败 |

所以第一层能覆盖前两种场景，第三种必须有第二、三层兜底。

### 第二层：探活判据 —— 双条件，缺一不可

```
判据 = 进程存在（pidof CrashCore）
     且
       API 可响应（wget --timeout=3 http://127.0.0.1:9999/proxies）
```

- **只有进程检查**：识别不了卡死。
- **只有 API 检查**：进程刚启动、API 未就绪时会误判，导致反复重启。
- **两者都满足才算健康**：能同时覆盖"进程没了"和"进程在但死了"两种失效。

`--timeout=3` 是刻意压短的：探活本身不能成为新的阻塞点，超时时间必须远小于用户感知阈值。

### 第三层：fail-open —— 连续失败后停在"最简可用态"

这是整套设计里最重要的决策：

```
连续失败 3 次 → 停止重试 → 摘掉 iptables 劫持链 → 退回纯 NAT 直连
```

为什么不是无限重试？

- 代理不可用时，无限重试只会让设备在"半挂"状态反复震荡，用户每次访问都要等超时；
- **退回纯 NAT 直连后，国内网络 100% 可用，境外不可用** ——这是一次明确的、可预期的降级；
- 对一个家庭网络来说，"能上国内网"的优先级永远高于"能翻墙"。

**这就是 fail-open 的本质：宁可少一个功能，不能整网不可用。**

### 先拆链，再重启

重启顺序不能反。正确顺序：

```
start.sh stop     ← 先摘掉 iptables 劫持链
（sleep 等待链清理完成）
start.sh start    ← 再拉起内核并重建链
```

如果先重启内核再改链，中间会存在一个窗口期：**iptables 链还在，7892 端口没人监听**。此时所有命中劫持规则的连接都会被立即 RST，用户侧表现为"突然全线报错"。

先拆链的意义是把这个窗口期的表现从"连接被拒"变成"正常直连"——同样是几秒钟，一个是报错，一个是照常用。

## 3. watchdog.sh 的四个设计要点

自研守护脚本约 1.5KB，cron 每分钟执行一次。四个设计值得单独说。

### 要点一：双条件探活

已在第二层说明。补充一点：API 探测用的是 `/proxies` 这个轻量端点，不触发任何代理行为，开销可忽略。

### 要点二：锁文件防并发

```
watchdog.lock
```

cron 每分钟触发，如果上一次执行还没结束（比如正在重启），下一次会正常启动并产生重叠操作，导致反复 stop/start。

加锁后，后到的实例直接退出。这是所有 cron 驱动脚本的必备项。

### 要点三：失败计数与放弃阈值

```
watchdog_failcnt：连续失败计数
达到 3 → 停止重试，保持纯 NAT 直连状态
```

计数器必须是**连续**失败，重启成功后清零。否则偶发抖动会累积成误判，导致守护脚本自己把网络降级掉。

### 要点四：心跳日志，区分两种"没生效"

脚本额外写一行：

```
echo "cron-alive $(date)" >> /tmp/cron_alive.log
```

这一行的作用不是记录脚本运行，而是**区分"cron 没跑"和"脚本逻辑错"**：

| 现象 | 判断 |
|---|---|
| 心跳日志没有新记录 | cron 本身没在跑（服务没起、crontab 丢失） |
| 心跳正常但无重启记录 | cron 在跑，脚本逻辑或判据有问题 |

没有这一行，出问题时只能靠猜。**这是整套脚本里成本最低、收益最高的一处设计。**

## 4. 如何验证隔离是否真的生效

不要等故障发生时才检查。日常就要能验证。

### 验证一：确认国内流量不进内核

```
# R3G 上查看连接表，观察国内目标是否出现
# 以及 iptables 命中计数
iptables -t nat -L shellcrash -v -n
```

命中计数应主要体现在境外目标对应的连接上。若国内访问也大量命中 7892，说明分流规则顺序有问题。

### 验证二：模拟内核卡死

```
# 暂停内核进程（不杀死，模拟卡死）
kill -STOP $(pidof CrashCore)

# 观察：国内访问表现、watchdog 是否在 1 分钟内完成降级

# 恢复
kill -CONT $(pidof CrashCore)
```

这个测试能一次性验证第二层判据和第三层兜底是否都工作正常。

### 验证三：确认降级后是"直连"而非"断网"

```
iptables -t nat -L PREROUTING -n
```

降级完成后，跳转到 `shellcrash` 链的规则应已被移除。此时 `ping` 国内地址、访问国内网站应完全正常。

## 5. 已知局限（如实记录）

以下几点是明确的短板，不掩盖：

| 局限 | 现状 | 影响 |
|---|---|---|
| **卡死场景未做长期实测** | 双条件判据是按"进程存活 ≠ 服务可用"的原理设计的，`kill -STOP` 验证过单次，未做长时间运行统计 | 判据有效性有原理支撑，但长期稳定性缺乏数据 |
| **降级期间境外全断** | fail-open 只保国内 | 用户需手动重启才能恢复代理 |
| **恢复不自动** | 连续 3 次失败后停止重试，不会在稍后自动再试 | 如果是上游临时故障（如机场短暂维护），需要人工干预 |
| **fake-ip 与面板配置可能不一致** | `configs/ShellCrash.cfg` 的 `dns_mod` 与 `yamls/config.yaml` 的 `enhanced-mode` 由不同路径管理，订阅导入会覆盖后者 | 会出现"面板显示一种模式、实际运行另一种"的情况，必须以 `config.yaml` 为准 |
| **无配置生成器** | 配置变更靠手工编辑 + `.bak_*` 备份 | 无版本管理，回溯成本高 |

### 关于 fake-ip 与面板配置不一致的具体说明

```
configs/ShellCrash.cfg : dns_mod=redir_host      ← 面板里的设置
yamls/config.yaml      : enhanced-mode: fake-ip  ← 实际生效的配置
```

根本原因在配置文件的链接结构，一共两级：

```
/etc/ShellCrash/config.yaml   ->   /etc/ShellCrash/tmp/config.yaml   ->   /etc/ShellCrash/yamls/config.yaml
      （符号链接）                        （符号链接）                          （真实文件）
```

真正存放配置的是 `yamls/config.yaml`（普通文件），`tmp/config.yaml` 也是链接而非实体副本。CrashCore 的启动参数为 `-f /etc/ShellCrash/tmp/config.yaml`，逐级解析后最终读写 `yamls/config.yaml`。这个文件在每次启动或订阅导入时都会被重新生成，面板里的 DNS 模式设置不会写回去。

**处置**：判断当前实际生效的 DNS 模式，永远看 `yamls/config.yaml`（`tmp/config.yaml` 只是指向它的链接），不要看面板。需要持久化修改时，应修改订阅转换模板或在导入后追加修改，而不是在面板里改。

## 6. 这套设计能覆盖什么，不能覆盖什么

| 场景 | 是否覆盖 | 说明 |
|---|---|---|
| 单个节点失效 | ✅ | `fallback` / `url-test` 组内自动切换 |
| 代理组全部失效 | ✅ | 国内不受影响，境外失败 |
| 内核进程崩溃 | ✅ | watchdog 重启，期间先拆链保直连 |
| 内核卡死无响应 | ⚠️ | 依赖 API 探活发现，1 分钟内降级；长期稳定性未统计 |
| 上游出口中断（R3G WAN 侧断） | ❌ | 全断，超出本设计的职责范围 |
| 主路由（下游）故障 | ❌ | 全断，与代理无关 |
| 双层 NAT 导致的 P2P 失败 | ❌ | 架构问题，只能靠减少 NAT 层数解决 |

**最后一行的说明**：串行级联部署下，终端实际处于双层 NAT 之后，UDP 打洞成功率低。这不是代理配置能解决的，也不能靠加 iptables 规则缓解。若 P2P 类应用（游戏对局、部分语音）表现异常，唯一根治路径是让主路由改为桥接 / AP 模式，把链路减为一层 NAT。
